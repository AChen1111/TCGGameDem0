## 根因：把区域内牌序当成场上格位

[ZoneRef](D:/GameWorkplace/Doing/TCGCardDem0/Assets/Scripts/Duel/Presentation/DuelPresentationContracts.cs:100) 的相等判断同时比较区域类型、玩家和 `Slot`。场景里的主卡组、额外卡组、墓地和除外区域各有一个锚点，锚点的 `Slot` 为 `0`；参见 [场景区域创建](D:/GameWorkplace/Doing/TCGCardDem0/Assets/Scripts/Editor/Duel/BattleSceneBuilder.Scene.cs:180)。

[PoseFor](D:/GameWorkplace/Doing/TCGCardDem0/Assets/Scripts/Duel/Presentation/BattleSceneController.cs:323) 的实际代码要求找到精确匹配的场景区域：

```csharp
// 项目实际代码：普通区域必须对应一个已配置的场景锚点。
position = card.Zone.Kind == DuelZone.Material
    ? RegionAnchor(view.Card(card.HostInstanceId).Zone)
    : m_zones.First(x => x.Zone.Equals(card.Zone)).Anchor.position;
```

修复前，[DuelNetworkProjection](D:/GameWorkplace/Doing/TCGCardDem0/Assets/Scripts/Duel/Presentation/DuelNetworkProjection.cs) 有两条错误映射路径：虚拟卡背把循环序号 `i` 写入区域 `Slot`；真实 DTO 则把不属于场上区域的旧 `Slot` 原样带入显示区域。区域内的卡牌顺序或移动前的格位不是区域锚点编号。主卡组第二张虚拟卡背因此不能匹配主卡组唯一的锚点，`First(...)` 抛出上述首个异常。

```csharp
// 修复前的本任务实现：把卡牌序号写进了区域身份。
for (var i = present; i < count; i++)
    cards.Add(new CardView(Handle("hidden:" + seat + ":" + zone + ":" + i), display,
        Hidden, new ZoneRef(zone, display, i), CardPosition.FaceDown, false,
        Array.Empty<ZoneRef>(), Array.Empty<CardPosition>()) { Known = false });

// 当前实际实现：非场上区域统一使用默认 Slot=0；句柄继续包含 i。
for (var i = present; i < count; i++)
    cards.Add(new CardView(Handle("hidden:" + seat + ":" + zone + ":" + i), display,
        Hidden, new ZoneRef(zone, display), CardPosition.FaceDown, false,
        Array.Empty<ZoneRef>(), Array.Empty<CardPosition>()) { Known = false });
```

虚拟卡背仍用 `hidden:席位:区域:序号` 的句柄区分显示实例，没有把所有卡背合并成同一张卡。真实 DTO 的当前映射同样只对场上区域保留格位：

```csharp
// 项目当前实际代码，省略方法外围。
var kind = LocalDuelSession.MapZone(card.Zone);
var slot = card.Zone == Core.DuelZone.ExtraMonster && Seat == 1
    ? 1 - card.Slot : card.Slot;
return kind is DuelZone.Monster or DuelZone.SpellTrap
    or DuelZone.Field or DuelZone.ExtraMonster
    ? new ZoneRef(kind, Display(card.Controller), slot)
    : new ZoneRef(kind, Display(card.Controller));
```

共享额外怪兽区域仍按观察席位翻转；区域规范化只修正非场上区域，不改变规则裁定或泄露隐藏卡牌身份。

## 为什么随后出现空引用与加载停滞

旧初始化先把 `m_ready` 设为 `true`，再执行布局。布局失败后，`Update()` 仍会处理输入，但 HUD 的 `OnOpen()` 尚未完成，`Scene.BindCutin(m_cutin)` 没有执行。因此 [InputPointer](D:/GameWorkplace/Doing/TCGCardDem0/Assets/Scripts/Duel/Presentation/BattleSceneController.cs:130) 中这行实际代码继续产生空引用：

```csharp
bool blocked = m_cutin.Playing || m_frame.IsWindowBusy
    || state.Animating || (state.Choice.Active && !state.Choice.IsResponse)
    || OverUI(point);
```

这不是用判空跳过 `m_cutin.Playing` 就能解决的问题。那样会隐藏初始化中断，让输入、HUD 和表现队列继续处于不一致状态。黑色遮罩也没有机会走到初始化结束时的隐藏调用。

修复后的初始化先成功建立场面，再等待 HUD 明确完成引用绑定，最后启动表现源并开放帧更新。当前实际顺序为：

```csharp
Rebuild(false, 0);
RefreshWorld(m_session.Current);
frame.ShowPanel(AddressKeys.Prefab.BattleHudPanel, new BattleHudProperties(this));
await m_hudReady.Task.AttachExternalCancellation(this.GetCancellationTokenOnDestroy());
m_session.Start();
m_ready = true;
SceneTransitionOverlay.Hide();
```

[BattleHudPanel.OnOpen](D:/GameWorkplace/Doing/TCGCardDem0/Assets/Scripts/Duel/Presentation/BattleHudPanel.cs:86) 在切入演出引用、操作控件和初始显示配置完成后调用 `Scene.CompleteHudInitialization()`。所需 UI 引用继续通过 Prefab 的序列化字段绑定，没有添加 `GetComponent` 或空引用跳过逻辑。

另外，控制器用独立的 `m_subscribed` 记录已经订阅表现源事件。即使初始化没有达到 `m_ready`，销毁时也会解除已经建立的订阅：

```csharp
// 项目实际语句摘录：订阅状态不依赖场景是否初始化成功。
m_session.Changed += OnChanged;
m_subscribed = true;

// OnDestroy 中的实际语句摘录，省略其他动画和视图清理。
if (!m_subscribed) return;
m_session.Changed -= OnChanged;
```

后续房间 `YY3WCKSE` 检查中，主动中断 Editor WebSocket 暴露了另外一处连接生命周期问题：底层连接中断可能抛出 `OperationCanceledException`，原本只有循环外围捕获取消异常，会直接结束整个重连任务。当前在单次连接范围内增加以下实际分支；房间会话未取消时，继续走原有重连循环：

```csharp
catch (OperationCanceledException) when (!token.IsCancellationRequested)
{
    if (generation != m_connectionGeneration) return;
    ALog.LogWarning("决斗连接已中断，准备重连", ALogCategories.Net);
}
```

更新后再次中断连接，Editor 自动恢复 `Open`，房间序号从 `10` 继续到 `12`，保持主要阶段。随后 Windows 玩家投降，双方房间与表现源最终显示终局，结果为“英雄获胜 · 投降”；双方退出后回到 `GameScene`，两账号回放列表包含相同的本次对局记录。

遇到同类问题时，先按这次启动会话定位第一条完整异常，跟到第一个项目栈帧，再沿初始化顺序解释后续异常。此例中先核对 `PoseFor` 的区域匹配输入，而不是从最后滚屏的 `InputPointer` 空引用开始改引用。截图保留为现象记录，运行日志和实际源码作为根因依据。
