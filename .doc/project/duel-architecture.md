# 决斗系统架构

> 更新：2026-09-09。设计规格，代码尚未落地。整体分层与现有 HTTP 后端的关系见 [系统架构](architecture.md)。
>
> 同步方式是经典确定性输入帧同步，传输自研 UDP。服务器与双方客户端运行同一套完整规则：服务器决定封帧顺序并运行参考副本，客户端按同一份输入自行计算，而不是只接收场面快照。
>
> 首版只做对决会话。账号、商城、匹配大厅仍由现有 HTTP 后端承担，决斗服务不复用那套 JWT / SQLite 启动依赖。
>
> 使用边界是可信好友原型。三端持有或能推导完整手牌、牌库顺序和随机状态；UI 按席位隐藏信息，不构成保密。本规格不承诺防作弊或公网安全。
>
> 本文给出卡牌、回合、响应、卡效扩展、重连和回放的必要模型。优先复用与可理解性，不追求高性能。现有登录、内容发布和数据库能力保持独立。

系统怎样分层写在这里；19 种卡分别怎样定义、每个效果如何发动和处理，见 [英雄卡组手册](hero-card-modeling.md)。两份文档配套使用，不把逐卡细节缩成一个通用 `OnUse`。

## 1. 首版到底做什么

做一条完整链：两人连接同一台服务器 → 使用预设英雄卡组开局 → 正常召唤、战斗、发动与响应 → 判定结束 → 保存回放文件。

| 做 | 首版不做 |
| --- | --- |
| 匿名创建对局、通过邀请口令加入 | 账号、登录、玩家资料、商城、经济系统 |
| 一个 ASP.NET 进程管理多场独立对局 | 匹配服务、公开房间列表、排行榜、管理后台 |
| 三端同核同输入，服务器权威封帧与参考裁定 | 玩家房主权威、P2P、NAT 穿透、主机迁移 |
| 自研 UDP 输入帧、必要补发和短时重连 | 网络插件、通用可靠传输框架、自研密码学、预测回滚 |
| 双方固定使用 40 主卡组 + 15 额外英雄样例 | 网络卡组编辑、收藏校验、全部现有卡片 |
| 内存对局、本地回放文件 | 数据库、跨进程恢复、跨服调度、回放云服务 |
| 单机与联网共用规则代码 | 任意 TCG 通用引擎、规则 DSL、卡文自动执行 |

“固定构筑”是首版会话配置，不是把卡名和容量写进引擎。以后开放构筑时，仍使用同一个 DeckValidator 和卡片模型。

同步策略采用服务器协调的确定性 lockstep：发同一份输入，各端自行计算，而不是持续同步场面。服务器截止封帧，不要求每帧等齐两人明确发来的操作；客户端只能执行已封口的完整帧。[N1]

规则目标仍是 Master Duel 的实际行为，但当前只有仓库内静态资料与官方 OCG / TCG 参考。未经实机确认的差异必须标为待验证，不承诺完整复刻所有裁定。

## 2. 最小后端与现有 HTTP API 的关系

### 2.1 独立的小服务，不改造整个现有 API

`Backend/src/AChen.Backend.Api` 是 ASP.NET Core / .NET 8 工程，启动会校验账号和内容发布配置，并执行数据库迁移。直接复用它的 `Program.cs`，做不到“只启动对决”。

决斗服务独立为 `AChen.Duel.Server`，仍用 ASP.NET Core / .NET 8，但拥有自己的入口：

- ASP.NET 宿主只提供进程生命周期、配置、日志和可选 /health。
- 用 UdpDuelService : BackgroundService 自建 UdpClient / Socket，监听一个 UDP 端口；装配内存会话、封帧器、参考内核和文件记录器。[N3][N4]
- 裸 UDP 不经过 Kestrel 的 HTTP 路由或 HTTP 限流；不把 HTTP/3 等同于自定义 UDP 协议。
- 不引用 AChen.Backend.Api，不需要 JWT、SQLite、发布密钥或内容管理服务。
- 现有 API、客户端登录与资源发布原样保留，不把数据迁进对战进程。
- 决斗开发入口使用本地对战地址、预设构筑与已准备的资源，不把登录、商城或卡组收藏作为进入对局的条件。客户端启动链若仍依赖内容服务，那是原有热更依赖，不能据此声称整套客户端已离线化。

### 2.2 一份规则源码，两种运行环境

| 拟新增位置 | 负责什么 |
| --- | --- |
| Assets/Scripts/Duel/Shared/Core | 卡牌状态、回合、时机、连锁、召唤和战斗 |
| Assets/Scripts/Duel/Shared/Cards | 卡定义、效果定义、处理器和融合配方 |
| Assets/Scripts/Duel/Shared/Session | ExecuteFrame、选择、局部 UI 投影、确定性状态摘要和回放 |
| Assets/Scripts/Duel/Shared/Contracts | 普通 DTO、ID 与枚举，不绑定序列化库 |
| Backend/src/AChen.Duel.Shared | 手工维护的共享项目，链接上述纯 C# 源码 |
| Backend/src/AChen.Duel.Server | ASP.NET 宿主、UDP 后台服务、封帧、补发、会话和文件适配 |
| Assets/Scripts/Network/Duel | UDP 收发、输入提交、帧缓冲、追帧和主线程分发 |
| Assets/Scripts/Duel/Presentation | 卡牌显示、选择面板、动画与音效 |

这些首先是目录和职责划分，不是要求每个目录一个 DLL。Unity 端仍可编入现有 HotUpdate.dll；后端引用共享项目，不引用整个 HotUpdate.dll 或 Unity 自动生成的 csproj。

共享项目首选 netstandard2.1 兼容范围，使用双方都支持的 C# 语法；具体 API、IL2CPP 和热更新兼容性须在实施时验证。[N5] 核心不得依赖 Unity、UniTask、ASP.NET、网络连接、数据库或全局日志单例。

首版不额外引入“网络桥接框架”或多个热更新业务 DLL。客户端先用小型平台连接适配器；若实际目标平台要求 AOT 包装，再只提取该适配器，而不是把网络类型带入卡效。

## 3. 只保留五个职责

| 模块 | 拥有什么 | 不做什么 |
| --- | --- | --- |
| Core | 各副本完整规则状态、合法性查询、流程与操作 | 不等待 socket，不播放动画 |
| Cards | 静态定义、能力拆分、卡效步骤 | 不发网络包，不操作 UI |
| DuelSession | 按封帧顺序单写入执行、选择、状态摘要、UI 投影 | 不按具体卡名分支裁定 |
| Transport / Protocol | UDP、席位绑定、封帧 / 缓冲、去重和补发 | 不根据客户端自报结果改 LP |
| Presentation | 可见场面、输入与可跳过动画 | 不持有可修改的完整 DuelState |

依赖和一次操作的路径：

~~~text
Unity UI → InputCommand → UDP → 服务器入队与统一封帧
                                  ↓ 同一份 FrameBundle
                     ┌────────────┼────────────┐
                服务器副本     客户端 A 副本    客户端 B 副本
                     └──── ExecuteFrame：同一套 Core + Cards ────┘
                                ↓ 各自计算相同规则状态
                         客户端按本席位投影到 UI
~~~

离线模式用本地封帧器直接产生 FrameBundle，仍走 ExecuteFrame 和本地 UI 投影。不写“单机卡效”和“联网卡效”两套实现。UI 提交后先显示“等待确认”，收到所属封帧之前不预测修改规则状态。

最少需要明确的契约：

- ExecuteFrame(frame)：按统一顺序重验输入、调用内核、生成结果和帧末摘要，三端共用。
- Advance(input)：在一帧内推进内核到下一稳定等待点、终局或故障；只有 ExecuteFrame 调用它。
- QueryLegalActions(player, context)：只读查询，不改变状态、不消耗随机数。
- SubmitAction / SubmitDecision：接收玩家意图或指定选择答案。
- Project(state, events, viewer)：输出该玩家可见的状态、事件与选择。
- AppendReplay(frame)：记录不可变封帧、帧末摘要及开局数据，不记录到包顺序。

异步只在会话外围。规则执行到一半需要玩家选卡时，保存数据化执行位置并返回；不能让一条网络连接或一个 await 持有唯一的规则执行现场。

## 4. 卡牌、卡组与区域

### 4.1 四种卡牌模型

| 模型 | 内容 |
| --- | --- |
| CardDefinition | 某种卡：稳定 ID、印刷属性、规则卡名 / 系列身份、卡种、能力列表、召唤条件、配方 |
| CardInstance | 某张实体：实例 ID、定义 ID、拥有者、控制者、区域、表示形式、存在期、运行记录 |
| CardPresentation | 中文名称、卡文、卡图与表现资源，不参与裁定 |
| CardView | 指定玩家目前可见的信息，不暴露内部对象引用 |

同名三张卡共享定义，但分别拥有实例和状态。CardId 不使用中文名、连接 ID 或 Unity 实例 ID。

重要字段不能省略：

- 拥有者与控制者分开；控制权变化不代表卡片换了拥有者。
- 原本攻击力、印刷攻击力和当前攻击力分开；属性由查询计算，不直接覆写公共 Attack。
- 等级、阶级、连接值、灵摆刻度分别建模；不存在守备力与守备力为零不同。
- 普通怪兽身份显式表达，不能以“当前没有生效效果”推导。
- CardRef = 实例 ID + 存在期 ID。卡离场再回来时，旧对象关系通常不能重新绑定；具体重置按规则政策，而非所有移动一律清空。

运行记录只保存有意义的数据：次数、召唤和攻击记录、正规召唤历史、计数物、关系、持续修正。哪些保留到离场后，由对应能力决定。

### 4.2 卡组不是场上的牌库列表

- DeckList：定义 ID 与数量，区分主卡组、额外及未来可选的副卡组。
- DeckSnapshot：开局校验后锁定的构筑和版本。
- DeckZone：本局创建实体后的有序牌库，三端副本按相同初始化得到相同顺序；UI 不显示牌序，但客户端内存无法保密。

DeckValidator 根据格式配置检查数量、区域、同名与禁限要求、卡片能力是否已支持。首版从服务器内置的英雄构筑创建两份快照，不接受客户端上传卡效脚本。

以后增加其他卡组，改定义包与构筑配置；不要改创建对局、同步或回放的主流程。尚未支持的能力应在开局前拒绝，不偷偷当作无效果怪兽。

### 4.3 区域与关系

ZoneRef 表达区域类别、归属和槽位 / 顺序；CardPosition 表达表里侧及攻守表示；BoardTopology 表达场地槽位与未来连接关系。UI 坐标不是规则坐标。

装备、素材和持续对象使用 CardRelation。超量素材不能被“场上怪兽”查询误计入；衍生物不具有普通实体的全部区域移动能力。

所有移区都经过规则操作，统一处理目的地替代、关系解除、重置和事实事件，禁止卡效直接修改区域列表。

### 4.4 隐藏信息

规则当前公开状态与某玩家曾经知道什么仍需分开，因为它们影响诱发资格和正确显示。UI 通过本地 Project(state, viewer) 只显示该玩家应当看到的牌与选择；未知牌不借显示 ID 提供正常界面的追踪功能。

但三端完整规则状态一致，输入帧也会包含对手的选择。这一投影只是 UI 与规则模块边界，不是对恶意客户端的安全边界。客户端可以读取内存或自行重算牌序；传输加密也不能向接收端隐藏其完整模拟所需的信息。

帧内规则引用使用三端一致的 CardRef、EffectId 和 DecisionId；不要发送某台客户端自己随机产生的显示对象 ID。若以后要求真正保密，需要另改同步模式，本版不同时维护第二套联网方案。

## 5. 对局状态与确定性

DuelState 最少保存：

| 状态组 | 内容 |
| --- | --- |
| 对局与版本 | 参与席位、规则包 / 卡片数据 / 格式版本 |
| 玩家与场面 | LP、卡实体、区域顺序、关系、修正与次数 |
| 回合与战斗 | 回合玩家、阶段、战斗步骤、伤害子步骤 |
| 时机与连锁 | 当前窗口、响应者、放弃记录、连锁项、触发候选、最后事件组 |
| 执行 | 流程帧、局部变量、未决选择、阶段待办 |
| 重演与结束 | 确定性随机状态、逻辑顺序、内部修订、终局或故障 |

每个副本每局独立一个状态；服务器一局一个串行队列，客户端按连续帧单写入推进。网络线程、计时器和 UI 不直接写入内核；不同局不共用随机数或次数记录。

内核不读取系统时间、渲染帧时间、网络延迟或 Unity 全局随机数。服务器在 StartRecord 中固定版本、构筑、先后手、FrameRate、随机算法及种子；三端按同一算法、调用顺序和稳定的候选顺序初始化。

确定性约束必须具体落地：整数 / 有理数运算与显式舍入；禁止依赖 Dictionary 枚举、进程 GetHashCode、地区格式和不受控浮点；卡实例、存在期、事件、动作上下文与 DecisionId 由共享计数器按规则执行顺序产生，不能各端自行 Guid.NewGuid。连接 ID 和请求随机 ID 属于外层输入，不冒充规则生成 ID。

每帧结束生成规范化 SHA-256 摘要：固定字段、字节序、字符串编码和集合排序，包含 FrameNo、所有规则状态、帧 / 决策计数器与随机状态；排除本机席位、网络队列、连接代次、墙钟、文件位置和动画。相同源码不自动等于跨运行时确定性，必须实际对照验证。

宿主超时、断线暂停 / 恢复 / 中断等形成封帧中的 SystemInput；认输是玩家输入。只有服务器能签发 SystemInput，客户端不自行读墙钟裁定。技术故障与规则败北分开；LP、抽卡失败和特殊胜利按规则位置判定，不统一等回合结束。牌库为空也不等于已经发生抽卡失败。

首版允许可变对象、遍历和重新计算；不要求 ECS、复杂缓存、全事件溯源或不可变状态框架。

## 6. 回合怎样建模

使用三个层次，不把所有情况塞进一个 Phase：

| 层次 | 示例 |
| --- | --- |
| TurnState | 抽卡、准备、主要 1、战斗、主要 2、结束 |
| BattleState | 开始、战斗、伤害、结束步骤；伤害步骤继续细分 |
| TimingState | 自由行动、组织诱发、建立连锁、结算、等待选择 |

主要阶段不等于能够通常召唤，还必须是允许该动作的时机并满足次数与限制。

TurnProcedure 管阶段路径、首回合限制、阶段跳过和未来额外回合。卡效提交明确的阶段修正，不直接设置 CurrentPhase。

准备 / 结束阶段用简单的 PhaseObligation 列表保存必须处理或可延后的事项：谁处理、在哪个节点、强制或可选、是否完成。不能把所有效果都放进 OnPhaseEnter 一次执行。

玩家申请换阶段时记录 PendingPhaseTransition，先走规定响应；对手发动后暂缓迁移，结算后重新检查，不直接跳阶段。

Pass 绑定当前窗口：

- 连锁建立时，双方连续放弃意味着开始逆序结算。
- 行动后快速响应中，双方放弃可能返回自由行动。
- 阶段迁移时，还要检查剩余阶段义务。
- 正在选素材或对象时，普通 Pass 不能替代必须完成的答案。

不实现“双方 Pass 就进入下一阶段”这一全局规则。官方时机图只能作为流程结构参考，MD 细节另行确认。[R1]

## 7. 每个效果怎样响应

### 7.1 事件不等于马上发动

~~~text
发生事实 → 保存事件与触发候选
         → 到规定检查点 → 组织诱发
         → 交接合法快速响应 → 建立连锁
         → 双方按窗口放弃 → 逆序处理整条连锁
         → 清理后到下一个检查点
~~~

DuelEvent 是事实，TimingCheckpoint 是允许观察和处理的位置，ResponseWindow 是某玩家当前能发动哪些能力。不能每产生事件、处理一步或结算一个连锁项就打开新连锁。

PendingTrigger 保存能力、事件组、源卡存在期、发生区域、相关控制关系和最后已知信息。“事件当时满足”与“现在能发动”分别检查；可选“时”效果可能错过时点，不能把候选当作迟早必须执行的任务。

TriggerPolicy 处理强制 / 可选、双方顺序、公开 / 非公开信息与版本差异。不能依订阅顺序排列诱发，也不能把所有手牌诱发都当快速效果。[R5]

### 7.2 连锁项与执行帧

ChainLink 保存发动者、能力 ID、源卡、模式、发动对象、已付成本和必要快照。发动无效、效果无效、不受影响和对象失效使用不同状态。

ProcessFrame 只保存流程 ID、步骤、局部值、操作结果和子流程关联，不保存 Unity 对象、Task、闭包或运行时函数指针。

DecisionRequest 保存 ID、回答席位、所属帧、选择类别、候选及组合约束。执行器遇到选择就挂起；答案合法才恢复同一帧。非法答案不重付成本，不恢复另一个效果，不重新进入自由响应。

发动前的可取消预选，与提交后不可撤回的手续分开。成本和对象按具体规则顺序执行；不能规定所有卡都先选对象或都先支付成本。

### 7.3 共同规则与单卡规则分工

| 公共执行器负责 | 单卡能力负责 |
| --- | --- |
| 谁获得响应机会、何时形成连锁 | 自己从哪里、满足什么条件可发动 |
| 何时组织诱发、如何逆序结算 | 触发事件、强制 / 可选、伤害步骤例外 |
| 挂起和恢复选卡 | 发动选对象还是处理时选卡 |
| 成本与操作的基础语义 | 处理步骤、前后依赖、哪些条件重验 |
| 维护修正与重置 | 来源依赖、持续期限和失效政策 |

源卡离场不自动取消已发动效果；处理时也不能重跑全部发动条件。效果可部分成功，后半失败不自动退还成本或回滚前半段。

## 8. 怎样编写一张卡

每张卡交付四项：CardDefinition、AbilityDefinition 列表、具名处理器或共用处理器参数、局面案例。AbilityDefinition 包含效果以及非效果的召唤条件等能力，不能全部当作可被无效的效果。

每个独立能力填写：

| 字段组 | 必须回答 |
| --- | --- |
| 分类与位置 | 发动效果 / 永续 / 召唤手续 / 非效果条件；来源卡种、区域、表侧要求 |
| 时机 | 自由行动或哪种事件；魔法速度；强制 / 可选；伤害步骤和错过时点条件 |
| 发动 | 条件、成本、发动对象、次数、计数发生节点 |
| 处理 | 需重验什么、每一步操作、处理中选择、依赖与部分失败 |
| 持续与证据 | 何时失效、是否依赖来源、裁定来源和待确认分支 |

一般处理器只需要 CanOffer、BuildActivation 和 Resolve 三类职责；具体接口按需要定义，不先造通用脚本语言。

英雄样例验证这些不同建模方式：

| 卡 | 应怎样表达 |
| --- | --- |
| 羽毛人等通常怪兽 | 数据定义，复用召唤和战斗，不写专属效果类 |
| 泡沫人 | 不入连锁的手牌召唤手续，与可选抽二诱发分开 |
| 狂野人 | 陷阱受影响性查询，不是一次“发动抗性” |
| 融合 / 奇迹融合 | 同一融合流程，不同素材区域和处置政策 |
| E / O | 处理时检索，与发动时取墓地对象分开 |
| H / R | 有期限数值修正；处理时重算数量和选择 |
| 英雄信号 / 英雄炸裂 | 指定战破送墓窗口，与不能在伤害步骤发动的通常陷阱分开 |
| 五种融合英雄 | 各自的召唤限制、战斗诱发、抗性或召唤诱发，不当作纯大怪 |

完整的 C01–C19 定义、字段、响应顺序、操作步骤与案例继续见[逐卡手册](hero-card-modeling.md)。不因简化后端而删除这部分内容。

以英雄炸裂为例：发动时选墓地通常英雄 → 入连锁、允许响应 → 处理时回手 → 成功后按当前局面选择符合攻击力条件的对手怪兽 → 尝试破坏。后一次选择不是发动对象，不开放新连锁；没有可破坏怪兽也不撤销已完成的回手。[R3]

联网时，三端执行到同一位置，产生相同 DecisionId 和候选；只有应答席位显示面板。答案作为输入，经服务器封帧后，各端一起恢复原执行帧。不是本机点击后立即执行、也不是对手不选卡就让对手的内核报错。卡效不接触 socket，不处理重试。

## 9. 改变规则的怪兽效果怎样扩展

基础操作共用：移动、抽卡、检索、展示、洗牌、丢弃、解放、破坏、除外、返回、召唤、伤害、回复、修正和选择。

破坏、解放、丢弃不是同一个 MoveCard：即使都送墓，原因与触发事件也不同。操作返回实际对象、实际目的地、成功原因及事件，而非一个 bool。

| 扩展点 | 例子 |
| --- | --- |
| ActivationPermission | 禁止发动、允许某特殊窗口 |
| ActionPermission | 禁止特殊召唤、攻击或取对象 |
| AffectabilityQuery | 狂野人不受作用于自身的陷阱效果影响 |
| OperationReplacement | 送墓改除外、破坏替代 |
| CharacteristicQuery | 原本值改变、加值、半值设定 |
| UsageAllowance | 额外通常召唤机会与不同次数限制 |
| SummonProcedure | 召唤手续、配方、正规召唤与固有限制 |
| TurnProcedureModifier | 跳过阶段、强制结束阶段 |

实现为少量类型化查询与处理函数即可，不必给每一种能力建设服务框架。不允许在网络、UI、战斗里各写一次卡名判断。

必须保留四个区别：

1. 能被选择，不等于受影响；陷阱不能影响狂野人，不等于整张陷阱无效。
2. 成本可支付性要考虑目的地替代；“送墓作为成本”不等于“丢弃作为成本”。
3. 来源依赖与期限分开；效果处理后持续的结果，不必因来源离场消失。
4. 属性加值与定值不能统一 SumBuffs；大龙卷的半值结果不是每次查询再乘一半。

多重替代、无效与抗性的依赖、属性叠加使用对应规则政策；一个万能 priority 不能解决全部裁定。遇到未支持或无法稳定求值的规则，记录技术故障，不用任意阈值判玩家败北。

## 10. 召唤与战斗

SummonProcedure 区分召唤尝试、允许的召唤无效窗口和召唤成功。正规召唤历史与“只能融合召唤”等固有限制分开。

普通融合与奇迹融合共用 FusionRecipe、素材组合校验和召唤流程。一张实体不能占两个素材角色；素材通常在效果处理时使用，不是发动成本。目的地替代后的实际移动结果由具体效果判断是否足以继续。[R4]

连锁处理中的融合召唤不能插入新的召唤无效连锁；其他“处理后立即召唤”机制需按其所处上下文另行判断。

战斗使用 AttackProcedure：

~~~text
攻击宣言与目标 → 宣言后的响应 → 必要的攻击卷回
             → 伤害步骤 → 战斗结束
~~~

伤害步骤分为开始、计算前、计算时、计算后、结束。里侧翻开、发动反转诱发、判定战破、实际送墓不是同一件事；允许发动哪些效果由节点许可决定，不是“所有二速都能发动”。[R2]

结果分别记录 LP 变化、战斗破坏判定、实际离场与目的地。攻击卷回是重新选择 / 继续攻击的规则判断，不是把整个对局状态回滚。攻击次数与宣言历史不能简单撤销。

## 11. UDP 经典确定性帧同步

### 11.1 服务器保留什么职责

保留精简后端：匿名双人会话、UDP 收发、输入排序与封帧、同一规则内核的参考副本、补帧日志、本地回放。不建设登录、匹配平台或数据库。

服务器是封帧与参考结果的权威，不是唯一运行规则的机器。客户端必须执行同一份输入才能得出自己的状态，不能把服务器的 LP / 场面结果当作平时的主要同步数据；服务端摘要用于发现分歧，不用于“修正到看起来相同”。

服务端与原生桌面客户端使用各自可用的 UdpClient / Socket API；net8.0 的异步重载不能假设 Unity 全部支持。首版验证桌面端 + 可信局域网。WebGL 无原生 UDP socket，不在首版范围。[N3][N6]

### 11.2 逻辑帧不是渲染帧，也不是规则响应时机

首版以 10 Hz 封帧，即每 100 ms 一次。这是可调工程起点，不是性能测量结论。

- FrameNo 是从 1 连续递增的模拟输入批次。
- 渲染可运行 60 / 120 FPS；UI 动画不写规则状态。
- 一帧可执行多个规则步骤直到等待输入；不是每帧只移动一张卡。
- 主要阶段、连锁、伤害步骤由规则推进，不随 FrameNo 自动变化。
- 玩家正在思考时，封帧和网络仍能继续；空帧不会替玩家操作。
- 客户端只需按顺序执行，不必与服务器在同一墙钟毫秒完成；缺帧就停规则执行，收发和动画仍可运行。

采用“服务器截止封帧”的输入 lockstep：服务器为没有新命令的席位写 NoInput，不等待两人各发一次明确空输入。只有收到服务器已封帧的 NoInput，客户端才知道它是真的空；未收到某帧时不能自行补空帧。[N1]

### 11.3 最小输入与帧结构

以下是契约示意，不是本次新增代码：

~~~text
InputCommand
  RequestId
  ActionContextId 或 DecisionId
  Kind: Action | Decision | Pass | Concede
  Parameters

FrameBundle
  DuelId
  FrameNo
  SystemInput: None | Pause | Resume | Interrupt
  SeatA: InputCommand | NoInput
  SeatB: InputCommand | NoInput
  ExpectedStateHash
~~~

服务器从绑定关系确定席位，不能信任输入自报的操作者。每席位每帧最多一个新请求；首版每席位只允许一个尚未封帧的请求，多出来的明确返回 Busy，不覆盖旧请求。重试相同请求不占新位置。

Rule Action 表达召唤、发动、攻击、阶段申请等意图；Decision 表达选对象、素材、顺序或模式。不能由客户端直接提交“已经造成多少伤害”。

NoInput 与 Pass 必须分开：

| 输入 | 语义 |
| --- | --- |
| NoInput | 本帧该席位没有新请求，不改变响应权或选择 |
| Pass | 玩家明确放弃当前 ActionContextId 对应的响应机会 |
| Decision | 回答特定 DecisionId，只恢复那个等待点 |

FrameBundle 的输入部分一旦封口就不可更改。ExpectedStateHash 在服务器执行该帧后补齐，再与同一份帧一起缓存和广播；帧摘要不是新的规则输入。

### 11.4 从点击到三端执行

1. 玩家在本地查询合法操作或回答当前选择，生成 RequestId。只更新“等待确认”的 UI，不直接改 DuelState。
2. UDP 服务校验会话、席位凭据、连接代次、类型、大小和频率，将新请求送入该局队列；相同 RequestId 查询已有状态。
3. 封帧时截止收集，按 SystemInput → A → B 固定顺序确定内容；缺少命令填 NoInput。这个排序不能替代诱发或响应优先权规则。
4. 服务器调用共享 ExecuteFrame，依次在当前规则上下文重新判断每条输入是否合法。第一条可能改变第二条的条件；三端都做同样判断，不能只在服务端预先悄悄修改状态。
5. 合法输入调用 Advance；不合法输入产生明确 Rejected，规则部分不变。执行到等待点、终局或故障，再写入帧号并生成摘要。
6. 服务器保存封帧、结果与请求状态，然后广播 FrameBundle。客户端收到后按连续帧执行相同 ExecuteFrame，比较帧末摘要。
7. 客户端由本地计算出的事件和状态更新 UI。两端规则计算相同，但本席位显示内容不同。

网络格式 / 权限校验不通过的包不入帧；已入帧但执行时规则不合法的请求仍保留在帧日志中，各端得到相同拒绝结果。不能只在回放中删去这些输入而假装帧内容未变。

晚到请求只能进入后续未封帧，使用原 ActionContextId / DecisionId 重验；不插入过去的帧，不转换为新局面的意图，也不做预测回滚。Ready、补帧 ACK 和心跳属于网络控制，不作为游戏动作塞入 A / B 槽位。

### 11.5 等待选择的实际例子

假设融合正在处理，三端都停在 DecisionId=D7，等待 A 选择素材：

| 帧 | 封帧内容 | 三端共同结果 |
| --- | --- | --- |
| 120 | 本帧先前输入使融合处理到选素材 | 产生 D7；只有 A 的 UI 展示选择 |
| 121 | A=NoInput，B=NoInput | 仍等待 D7，不自动 Pass 或送素材 |
| 122 | A=Decision(R42, D7, 素材答案)，B=NoInput | 三端校验同一组合并恢复同一流程 |
| 123 | 没有新请求 | 按已有等待点保持状态 |

如果 A 先收到 123、缺少 122，缓存 123 并请求补 122；不得跳到 123。如果 A 重发 R42，服务器只告知它已属于 122，不再排到 124。若新请求回答过期 D7，则在其所属帧中明确拒绝，不重付成本。

关键点：玩家尚未选择是合法的规则等待；丢失网络帧是副本暂时不能继续，两者不是一回事。

### 11.6 只实现本游戏需要的可靠性

UDP 不保证可靠、去重或有序，重传也必须受流量控制；大包依赖 IP 分片会降低可靠性。[N2] 不写通用 TCP 替代库，只实现三个小机制：

| 数据 | 如何确认和补发 |
| --- | --- |
| 创建 / 加入 / 准备 / 恢复等控制请求 | ControlRequestId 幂等；同请求重发返回原结果；明确状态与超时 |
| 玩家输入 | RequestId 幂等；返回 Queued、Framed(FrameNo) 或拒绝；对应帧执行后才有 Applied / Rejected |
| 服务器封帧 | 客户端确认连续已收到前缀，缺口请求帧范围，服务器从缓存限速补发 |

幂等键使用 (DuelId, SeatId, RequestId)，跨重连保留。同 ID 同负载不进入第二个帧；同 ID 不同负载拒绝；不能因连接变化清掉已封帧请求的记录。可对多余或格式错误请求有界保存拒绝结果，不能让垃圾请求无限占内存。

Queued / Framed 不是卡效执行成功，帧 ACK 也不是状态一致。客户端通过执行该帧得到输入结果；查询旧请求时先查幂等记录，再考虑其上下文是否过期，避免把成功的重发误报为失败。

客户端维护两个不同游标：

- LastContiguousReceivedFrame：从开局或恢复基线连续收齐到哪帧；收到 102 但缺 101 时，只能确认到 100。
- LastExecutedFrame：已经顺序执行并完成摘要比较到哪帧；不能以“已接收”冒充已执行。

两者可随心跳重复报告。ACK 丢失只导致重复补发；重复帧只检查一致并丢弃。相同 FrameNo 若内容不同，停止本局并报协议故障，不能任选一个继续。

### 11.7 小包、有界缓存与发送节奏

首版使用显式字段的紧凑二进制消息：固定整数宽度与字节序，字符串用 UTF-8 与长度前缀，枚举和数组长度校验。禁止 CLR 类型名或任意对象图；摘要序列化独立于网络封套。

首版起始约束：

| 项目 | 起始约束 |
| --- | --- |
| 单个 UDP 应用数据报 | 最多 1200 字节，包含本协议头；不是任意网络都不分片的保证 |
| 玩家输入编码 | 最多 384 字节；超过就明确拒绝，不静默截断 |
| 封帧编码 | 帧头、系统输入、两席位输入、摘要合计不超过 1100 字节 |
| 开局与控制消息 | 同样必须放进单数据报；大卡片定义包预先随程序准备，不走 UDP |
| 未来帧缓冲 | 有界，例如 256 帧；不能无限接纳远未来帧 |
| 一局帧日志 | 2 小时、72,000 个常规帧，并有字节上限；预留终止控制帧空间 |
| 初次重试间隔 | 例如 200 ms；逐次退避到上限，不按每次 Update 狂发 |
| 断线宽限 / 终局保留 | 180 秒 / 5 分钟，可配置 |

首版不做大消息分块重组：英雄样例的输入和 StartRecord 应能放入上述边界；必须通过编码尺寸检查确认。补帧发送多个独立 FrameBundle，不能把整份历史或快照塞进一个 UDP 包。未来大选择可扩展为规则层的分步选择，或单独增加受限分块协议，不能去掉包大小限制。

新帧、控制、重试、ACK 和追帧统一计入每端发送预算；限制在途帧窗口，优先补最早缺口，在丢包、RTT 上升时降低发送节奏并退避，连续失败则转离线。客户端失去帧但仍在回心跳时，也要按执行进度差与恢复时限判定是否跟得上，不能只看 socket 是否有流量。

控制消息与新帧不能被大规模追帧完全饿死；不同对局不被一个慢端阻塞。到达会话 / 帧日志 / 字节上限时，用保留空间封出 Interrupt 并结束会话，或在无法运行内核时明确技术故障；不无限缓存、不删除客户端还需要的日志后假装可恢复。

### 11.8 开局、凭据与恢复

首版匿名会话状态为 WaitingPlayers → Running → Finished / Interrupted。UDP 没有真正连接对象，PeerBinding 保存远端地址、席位、凭据、连接代次、心跳和确认游标；关闭本机 socket 不等于对局结束。

创建 / 加入 / 准备沿用一个简单流程：

1. Create 返回 DuelId、A 的席位凭据和不可猜测的邀请口令；Join 用邀请口令预留 B 并返回 B 的凭据。
2. 客户端保留自己的凭据后发 Ready；未确认的预留 30 秒后释放。重复 Create / Join 依 ControlRequestId 返回同一结果，不能因 UDP 重发创建多局。
3. 服务端准备同一 StartRecord：协议、规则与卡片版本、双方预设构筑、先后手、随机算法与种子、10 Hz 配置。
4. 两端确认收到 StartRecord 并完成初始化，以 StartAck 确认初始状态摘要。只有两端与服务器都匹配，服务器才从帧 1 开始；开局消息丢失时重发同一份，不能重新随机洗牌。

控制请求的去重身份由客户端本次进入随机 nonce 与 ControlRequestId 共同标识，首版限时缓存；缓存已过期的重试明确失败或创建新请求，不宣称永久幂等。持有席位凭据后，控制请求按席位归属验证。

凭据由平台安全随机数生成，不是用户 ID 或卡片 ID；不写入帧日志、回放或普通日志。首版可信局域网协议不加密，明文凭据不能抵御抓包和中间人；对局 ID 和 UDP 源地址也不能作为安全认证。服务器仅对已完成握手的席位发完整帧，限制未建会话请求频率与响应大小。本版不提供公网匿名服务。

恢复时携带本席位凭据、LastExecutedFrame 和对应摘要；服务端串行重新绑定地址并提升 PeerEpoch，旧代次包失效。旧代次尚未封帧的输入取消并更新请求状态；已经封帧的绝不能撤回，新的连接仍执行它们。重试凭据在本局保持稳定，恢复应答丢失后可以重新请求；不得依赖一次不可重试的令牌轮换。

短时丢包只补帧，不必立即暂停全局。判定一方离线 / 明显落后时，服务器封出 SystemInput.Pause；之后只允许 NoInput 和系统控制，保留未决选择，双方新游戏动作不能推进。空帧可继续编号，暂停不等于因网络故障判负。

恢复路径只有两条：

- 本地状态仍在且帧末摘要匹配：补发 LastExecutedFrame+1 起的原始封帧，追到服务器检查点。
- 本地状态丢失：用同一 StartRecord 和从头封帧日志快速重演；不播放历史动画，不启用历史选择面板，选择答案从帧中获得。

服务器验证追帧进度与摘要后封出 SystemInput.Resume，再允许游戏动作。网络仍可发送 / 确认期间，规则不能靠本地时间自行恢复。宽限到期封 Interrupt，不把断线默认判作规则败北。

首版不做中途状态快照。历史不全、规则版本缺失、凭据丢失或服务器进程重启时明确无法恢复。摘要不一致时停止并保存诊断；可以在隔离副本从头重演定位，但不能悄悄覆盖本地状态后声称始终一致。

### 11.9 三个能力边界

- 1200 字节与 10 Hz 是设计起点，不是通用最优值；实际需用目标网络做尺寸、丢包与吞吐验证。
- 服务器继续跑参考内核可拒绝非法命令与发现分歧，但不能阻止客户端读取已拥有的秘密，也不能靠一致摘要证明玩家没作弊。
- 如后续要求公网，先补标准安全握手、消息认证与抗重放、地址验证、反射放大和拥塞控制验收；不自行设计密码算法。那是单独扩展，不伪装首版已经具备。

## 12. 回放也先做最小版

只增加文件记录器，不做回放账号权限、列表服务、下载站点或数据库。首版“回放”指自研记录，不兼容 MD 原生格式。

区分两个用途：

| 类型 | 保存什么 | 能证明什么 |
| --- | --- | --- |
| 规则重演 | StartRecord、连续封帧、每帧摘要及终局标记 | 用同版本 ExecuteFrame 重新运行并对比三端结果 |
| 记录播放 | 某授权视角的事件和展示快照 | 展示当时过程，不等于重新验证规则 |

首版先从头重演，不做任意时间跳转。规则包、卡片数据、格式与 ReplaySchemaVersion 都要记录；规则版本缺失则拒绝重演，不能偷偷用新卡效执行旧输入。

回放记录来自不可变封帧，不来自 UDP 到包顺序。心跳、ACK、连接代次、凭据和重复传输不记录；已经封帧的全部输入（包含执行时被规则拒绝的输入）、NoInput 和 SystemInput 按原顺序保留。未入帧的非法网络包只进入有界诊断日志。

空帧首版直接记录即可；将来压缩空帧时必须保留精确帧号区间与等价重演语义。播放可以快进或暂停，重演仍不能跳过会改变逻辑游标或系统控制的帧。

文件由 StartRecord、递增帧记录和结束标记组成，服务端保留参考记录，客户端也可记录自己接收并执行的完整帧。它们包含或能推导双方秘密，符合本版信任边界；分享文件即可能公开整局牌序。普通回放 UI 默认按玩家视角显示，不因此声称文件本身保密。

文件写入失败标记 ReplayIncomplete 并记录诊断，已经执行的卡效不回滚；“帧已执行”不等于“回放已落盘”。缺结束标记的文件按不完整记录处理，禁止伪装正常完局。

以后需要中途跳转或崩溃恢复，再增加完整检查点：不只保存场面，还必须包含流程帧、连锁、选择、修正、次数、阶段待办、随机状态、FrameNo 与确定性 ID 计数器。只有要恢复在线会话时，才还需要幂等记录等会话数据；连接句柄和凭据不属于规则快照。

## 13. 表现层与排错

- UI 只显示本席位 CardView；其数据来自本地内核执行已封帧后的结果。服务器是封帧和参考结果的权威，客户端也真实运行完整裁定，而非只显示服务器快照。
- 表现按本地规则事件的可见投影播放，再向本地计算出的视图收敛；跳过动画、低帧率、重建面板不改变规则。帧号和事件序号防止补帧、追帧时重复播放。
- 选择面板绑定确定性 DecisionId。恢复追帧时先隐藏交互，到当前有效等待点才重建；收到未来帧不立即弹出其中的面板。UDP 收包只入有界缓冲，顺序执行后才向 Unity 主线程分发表现。
- AI 如果以后加入，也只使用所扮演席位的合法输入和视图；核心不需要为 AI 再复制一套规则。
- 内核返回结构化诊断。Unity 外层用 ALog / ALogCategories，ASP.NET 外层用自身日志适配；记录创建、提交 / 拒绝、连锁、重连、中断和保存失败，不输出凭据或完整秘密状态。
- 技术错误、网络中断、规则不支持和正常胜负使用不同原因，不将故障都归为玩家失败。

## 14. 怎么验证这个方案

### 14.1 当前验证到哪一步

已完成目录结构静态核对、官方规则参考核对、协议模型审查与以下纸面推演。没有可运行实现，未经编译或测试验收，也没有完成 MD 实机一致性验证。

规则证据分为官方 OCG / TCG 参考、工程推导、待确认；只有具备具体 MD 版本和对局证据后，才能标记 MDObserved。独立审查不能代替运行验收。

### 14.2 关键纸面推演

| 案例 | 初始条件与输入 | 模型应得到的结果 |
| --- | --- | --- |
| V01 英雄炸裂部分处理 | 合法墓地对象仍在；对手连锁后没有可破坏怪兽 | 对象回手成功，后段不破坏，不回滚回手；参考官方 FAQ [R3] |
| V02 融合目的地替代 | 素材处理允许且存在送墓改除外 | 按实际素材结果处理，不因未送墓一律失败、不插入新连锁；参考 [R4] |
| V03 选择重发 | R42 已封入 122 帧并回答 D7，回执丢失 | 同 R42 不进入第二帧；相同 ID 改答案拒绝；卡效只执行一次 |
| V04 UDP 乱序 | 已执行 100，先收 102 再收 101 | 缓存 102，只 ACK 连续到 100；补齐后依次执行 101、102 |
| V05 无输入与 Pass | D7 等选素材，连续 20 帧 NoInput | 仍等待 D7，不自动放弃、结束阶段或送素材 |
| V06 同帧交互 | A 的输入改变响应窗口，B 输入仍指旧窗口 | 三端按相同顺序执行，B 得到同一拒绝；服务器不私自适配 B 的输入 |
| V07 追帧 | 客户端执行至 100 后断线，服务器保留完整记录 | 摘要相符时补 101 起原始帧；历史选择从帧读取，不再问玩家 |
| V08 初始数据 / Ready 重发 | 开局消息丢失又重发 | 不二次占座、不重新生成随机种子；初始摘要匹配后只启动一次 |
| V09 旧地址包 | 已恢复新 PeerEpoch，旧端点仍重发请求 | 未封帧的旧代次请求失效；已封帧命令不撤销或重复执行 |
| V10 摘要分歧或宿主丢失 | 一端状态摘要不同，或服务器内存对局消失 | 明确停止 / 无法恢复，不用 UI 快照掩盖，不伪造正常胜负 |

V03–V10 是工程状态推演，只说明协议约束相容，不表示 UDP 故障测试已通过。

### 14.3 实现以后必须验收

1. 回合推进、双 Pass、阶段待办、伤害步骤和连锁中的诱发走正确检查点；空逻辑帧不制造规则时机。
2. 19 种英雄逐卡验证正常、对象 / 来源改变、部分失败与时机例外；手册待核验分支关闭后才宣称完整支持。
3. 固定 StartRecord 和 FrameLog，在 Unity 原生 Player、ASP.NET 参考副本、回放中逐帧比对摘要；覆盖随机洗牌、ID 分配和数值舍入。
4. 模拟丢包、重复、乱序、ACK 丢失、迟到输入、控制消息重发和帧冲突；不得跳帧、重复执行或混淆 NoInput / Pass。
5. 不同渲染 FPS、动画跳过及追帧速度得到相同规则摘要；只有表现进度不同。
6. 断线补帧与从头重演的恢复结果一致；版本缺失、历史缺失和摘要分歧必须明确失败。
7. 检查正常 UI 不错误显示对手信息，同时明确客户端内存 / 帧记录能读取完整信息，不把这一已接受边界写成“防作弊通过”。
8. 限制数据报、在途窗口、补发流量、未来帧缓冲和会话日志；慢端和重试不能无限增长资源。
9. 文件写入失败、异常帧、执行异常和进程退出有可诊断结果。网络保护阈值不冒充游戏规则。
10. 增加限制召唤、额外通常召唤、目的地替代、无效、属性设定各一个案例，确认不用改封帧和 UDP 协议就能扩展。

## 15. 按什么顺序实现

| 阶段 | 最少交付 | 完成标准 |
| --- | --- | --- |
| A 规则骨架 | 卡 / 卡组 / 区域、回合、普通动作、确定性 ID / 随机 | 脱离 Unity 可推进普通怪兽对局 |
| B 响应和写卡 | 执行帧、选择、连锁、操作与英雄处理器 | 逐卡案例有明确结果，不在错误时点响应 |
| C 本地帧执行 | ExecuteFrame、StartRecord、帧日志、Unity 视图和交互 | 同帧日志逐帧摘要一致，动画可跳过 |
| D UDP 帧同步 | 独立服务、匿名双人、10 Hz 封帧、重发去重与补帧 | 三端按同一封帧计算；不依赖现有 HTTP API 或数据库 |
| E 恢复与验收 | 追帧、从头重演、摘要对照、清理和文件失败处理 | 第 14 节相应验收通过后才称可用好友原型 |

开发早期先做目标 Player 的 UDP 往返，以及同一小段 FrameLog 的跨运行时摘要对照，尽早排除传输与确定性障碍，再填充完整 D 阶段。

高复用的验收标准是：普通新卡只增加定义与效果组合；新机制只扩展对应规则模块；新平台只替换连接 / 显示适配。不是提前把账号、房间平台、插件系统和分布式服务都建出来。
