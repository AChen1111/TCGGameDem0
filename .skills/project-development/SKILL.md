# Rules

- 明确、低风险、易回退的任务直接处理；不做无关推演或过度设计。
- 除非用户明确要求，否则一律不跑测试，也不检查编译正确性。不调用 `recompile`、`recompile_status`、`run_tests`、`dotnet test`，也不通过控制台错误日志核对编译结果。
- 当需求存在歧义、关键信息缺失，或存在多种会显著影响实现结果的合理方案时，必须弹出选项框向用户确认，并简要说明各选项的影响；在用户明确选择前，不得自行假设或替用户作出决策。
- 游戏开发优先用 Unity Editor 或 Unity Pipeline 修改场景、预制体、组件参数、资源和项目设置；仅在 Unity 操作无法实现所需行为时编码。
- 新增或修改代码时，只为非显而易见的关键逻辑、约束和特殊处理添加简短中文注释；注释使用英文标点，不复述代码。
- 新增或修改业务功能时，在关键操作完成、状态变更、失败或降级节点使用 `ALog` 记录操作名称、作用对象、执行结果及排查所需的关键参数，并使用 `ALogCategories` 分类；按情况选择 `Log`、`LogWarning` 或 `LogError`。避免在 `Update`、循环、属性访问等高频位置记录，不重复记录同一事件，不输出密码、令牌等敏感信息，不为纯数据结构或简单工具方法机械添加日志。
- 保持实现简单、整洁、少抽象；不为缺乏现实依据的假设增加分支或防御代码，但必须处理高概率或高影响边界。
- 若读取并采用 `.doc/` 文档，最终回复增加“文档依据”，列出路径及相关内容概述；仅在必要时短引原文，不复制全文或无关内容。
- 若读取或使用 Skill，最终回复末行输出 `Skills: <name>（项目）, <name>（全局）`；仅列实际使用项，无则省略。
